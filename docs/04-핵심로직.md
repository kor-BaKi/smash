> 최종 갱신: 2026-11. 구현된 코드 기준으로 정리했다. 엔진 1·2는 단위 테스트로 검증한다(전체 157개).

## 엔진 1 — 자동 조 배정

입력: 미배정 부원들 + 각자의 가능 요일조(복수)
목표: 가능 조 중 하나에 배정, 조별 인원 최대한 균등
제약: 선택지 적은 부원부터 먼저 배정 (결정적)

```
function autoAssign(members, groups):
    for m in members: m.optionCount = count(m.availableGroups)
    sorted = sort(members, by=[optionCount ASC, id ASC])   # 결정적
    groupCount = { g.id: 0 for g in groups }
    assignments, unassigned = [], []
    for m in sorted:
        if m.availableGroups is empty:
            unassigned.add(m, reason=NO_AVAILABILITY); continue
        target = minBy(m.availableGroups, key=[groupCount[g], g.id])  # 인원 적은 조, 동점 id순
        assignments.add(m -> target); groupCount[target] += 1
    return { assignments, unassigned, groupCount }
```

설계 근거: 그리디 + 결정적(동점 id순) + O(N log N). N=250, G=10이라 충분.
"선택지 적은 부원 먼저"는 임원 수작업을 그대로 코드화한 것.

**preview / confirm 2단계**: preview는 DB를 바꾸지 않고 결과만 보여주며, 임원이 수정한 뒤 confirm에서 확정한다.
confirm은 (1) 대상이 아직 미배정 ACTIVE인지 재조회, (2) preview 시점의 대상 목록과 현재 목록 비교(달라지면 ASSIGNMENT_CONFLICT),
(3) 이미 배정된 건은 건너뛰기(중복 확정 방지), (4) 없는 조가 섞이면 전체 롤백을 보장한다. 단일 트랜잭션, `group_id IS NULL` 조건부 UPDATE로 동시성을 막는다.

테스트:
- TC1 전원 전체조 가능 → 각 조 ±1
- TC2 1개만 고른 부원 → 해당 조 배정
- TC3 미제출 → unassigned(NO_AVAILABILITY)
- TC4 동일입력 2회 → 결과 동일(결정성)
- TC5 253명/10조 → 최대-최소 ≤ 2

### ① 버튼 분기

resolveButtons(member, activity):

API에는 ATTEND로 노출하고 DB에는 REGULAR로 저장한다(DTO 변환 계층).

### ② 이월 후보
```
getCarryoverCandidates(member, currentActivity):
    monthStart, monthEnd = monthRange(currentActivity.date)
    myActs = Activity where group=member.group_id, date in [monthStart,monthEnd], not cancelled
    candidates = []
    for act in myActs:
        if hasCarryoverOut(member, act): continue          # 이미 자격 뺀 날 제외
        if act.date > today: candidates.add(act, FUTURE)
        elif act.date < today:
            if not hasRegularAttend(member, act): candidates.add(act, PAST_ABSENT)
    return candidates   # 빈 배열이면 "이월 불가"
```
**이월 규칙의 의미**: 이월은 "이번 달에 이미 빠진 날을 같은 달 안에서 보충"하는 제도다.
당일(today) 활동은 후보에서 제외되고, 다음 달 활동은 후보가 아니다. 이중 이월은 서버 검증(INVALID_CARRYOVER_TARGET)과
DB 유니크 제약 `(user_id, carryover_target_activity_id)`로 이중 방어한다.
**이월 취소**는 별도 상태 변경 없이 Participation 기록 삭제만으로 해당 날의 자격이 복구된다(계산 기반 설계의 이점).

### ③ 충족 계산 (임원 전용)
```
calculateFulfillment(member, year, month):
    range = monthRange(year, month)
    guaranteed = count Activity where group=member.group_id, date in range,
                 not cancelled, type=REGULAR
    fulfilled = count Participation where user=member,
                activity.date in range, type in [REGULAR, CARRYOVER]
    shortfall = max(0, guaranteed - fulfilled)
    return { guaranteed, fulfilled, shortfall }
# OTHER_GROUP, FREE_ATTEND, ABSENT 제외. CARRYOVER는 충족 1회 인정.
```

테스트:
- TC1 본인조 ATTEND → 충족+1
- TC2 사전이월 → 해당 날 버튼 [CARRYOVER,OTHER_GROUP], 충족+1
- TC3 사후이월 → 과거 미참여일 PAST_ABSENT 후보로 뜸
- TC4 이미 참여한 과거일 → 후보 제외
- TC5 타조참 → 충족 변화 없음
- TC6 이월취소(기록삭제) → target [ATTEND,ABSENT] 복구
- TC7 당월 경계 → 다음달 활동 후보 제외
- TC8 자격 다 씀 → 후보 빈 배열
- TC9 이미 이월에 쓴 날짜 재선택 → INVALID_CARRYOVER_TARGET

## 활동 캘린더 (조회 전용 투영)
"내 조의 한 달"을 보여주기 위해 **실제 Activity 행 + 아직 생성되지 않은 미래 예정일**을 합쳐 반환한다.
스케줄러는 당일 행만 만들기 때문에, 미래 날짜는 계산으로 보여준다.

```
activityCalendar(me, year, month):
    group = me.group
    real = Activity where group, date in month
    days = real -> {date, activityId, activityType, isCancelled, isProjected:false}
    for d in dates(month) where d > today and d.dayOfWeek == group.dayOfWeek:
        if activeSchedule(group) exists and d not in real.dates:
            days.add({date:d, activityId:null,
                      activityType: FREE if d in freePeriods else REGULAR, isProjected:true})
    return { year, month, myGroup, activities:days, freePeriods }
```
- 배정 전이면 `myGroup=null`, 활동 목록은 비어 있다.
- 자유활동 기간은 별도 배열로도 내려 달력 배경 표시에 쓴다.

## 푸시 알림
- 종류: 투표(POLL) / 정산(SETTLEMENT) / 활동(ACTIVITY). 사용자별 종류 on/off 설정(`/notification/setting`).
- 모든 푸시에 `data` payload를 실어 앱이 탭 시 해당 화면으로 이동하게 한다 (모든 값은 문자열).
  - POLL `{pollId}` / SETTLEMENT `{activityId, transportGroupId}` / ACTIVITY `{activityId}`
- 투표 생성·정산 생성은 `sendNotification` 플래그로 알림 발송 여부를 선택한다.
- 다기기 로그인을 위해 한 사용자에 토큰 여러 개를 허용하고, 같은 기기에서 다른 계정으로 로그인하면 토큰이 새 계정으로 이전된다.

## 인증·보안 로직
```
login:  lockedOut(studentNo)? → 429 TOO_MANY_ATTEMPTS
        ACTIVE만 허용, 비밀번호 BCrypt 대조 → 실패 시 카운트 증가(5회/10분), 성공 시 초기화
refresh: JWT 서명·만료·typ=refresh 검증 → sha256(token)으로 서버 저장값 대조
         → 새 access + 새 refresh 발급, 기존 폐기(Rotation)
logout: 저장된 refresh 삭제 (access는 만료까지 유효, 30분)
```
- 로그인 시도 제한은 인메모리(단일 서버 가정). 서버를 늘릴 때는 Redis 등 외부 저장소로 옮겨야 한다.
- 탈퇴·비밀번호 변경은 현재 비밀번호를 다시 확인하고, 같은 실패 제한을 공유한다.
